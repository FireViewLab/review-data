# 크롤러 및 저장 개선

## 네이버 리뷰 미수신

최근7일 네이버 리뷰 실패128건은 리뷰 목록 미수신이며 상품에 양수 리뷰 수가 존재했다. locknlock:13781489400의 기존 코드를 읽기 전용으로 재현한 결과 기존 숫자 포함 탭 선택과 일반 리뷰 경로가 실제 화면의 숫자 없는 리뷰 탭·group-products/query-pages 경로를 놓쳤다.

숫자 없는 리뷰 탭을 우선 선택하고 숫자·괄호 포함 탭도 지원한다. 응답 URL은 쿼리 문자열을 제외한 경로로 비교하며 기존 및 묶음 경로만 허용한다. 묶음 응답은 productNo를 우선하고 없는 경우 originProductNo로 요청 상품과 비교한다. 묶음 응답의 식별값 없는 행은 저장하지 않는다. 작성자 식별값은 기존처럼 저장하지 않는다.

수정 코드를 같은 운영 환경에서 읽기 전용 실행하여 상품 리뷰 수1건·수집1건을 확인했다. 묶음 응답8건 중 요청 상품1건만 반환했다. 검증에서는 DB 저장·AI 요청·Backfill 제어를 하지 않았다. 아직 리뷰 탭 첫 페이지 수집이며 전체 페이지 수집을 구현한 것으로 해석하지 않는다.

## 리뷰 저장 최적화 (#110)

- 정규화·동일 ID 마지막 관측 선택 이후 500건씩 upsert한다. asyncpg 바인드 제한을 넘는 3,000건 입력도 저장 가능하다.
- 모든 배치는 기존 상품 잠금과 같은 트랜잭션을 사용한다. 중간 실패 또는 rollback 시 부분 저장을 남기지 않는다.
- 내용·별점·작성자·작성일·옵션·이미지·도움 수가 같으면 `updated_at`과 상품의 `analysis_input_hash`를 보존하고 `last_collected_at`만 갱신한다.
- 새 리뷰 또는 값 변경 시 분석 입력 캐시를 무효화한다. 도움 수만 변경된 경우도 보수적으로 무효화하되, 분석 예약 단계의 입력 해시 비교가 불필요한 재분석을 막는다.
- 기존 복합 기본키의 ON CONFLICT 경로를 유지하며 새로운 인덱스나 데이터 삭제를 요구하지 않는다.
- PostgreSQL 16 통합 테스트에서 별점 4.1의 동일 재관측, 변경 감지, 3,000건 분할 저장, 중복 ID 마지막 관측, 전체 rollback을 확인했다.

## 수집 실패와 재예약 (#111)

`collection_jobs.failure_kind`와 `retry_after`를 추가한다. 최신 종료 작업이 실패한 경우에만 정기 재예약을 미룬다. 수동 요청은 기존과 같이 큐에 넣을 수 있으며, 이후 성공하면 과거 대기는 적용하지 않고 연속 실패 횟수를 초기화한다.

기본 설정 `SCHEDULE_FAILURE_COOLDOWN_SECONDS=21600`에서 첫 실패 대기는 다음과 같다.

| 원인 | 첫 대기 |
| --- | --- |
| 접근 차단·요청 제한 | 6시간 |
| 시간 초과·네트워크/서버 오류·DB 저장 실패 | 10분 |
| 응답 파싱·기타 오류 | 1시간 |
| 인증 설정 필요·미지원·404/410 | 24시간 |

연속 실패마다 대기를 두 배로 늘리되 최대 24시간으로 제한한다. 위 설정이 0이면 새 실패의 대기를 끈다. lease 시도 상한 초과는 시간 초과로 기록하고 1시간 대기한다. 기존 미분류 이력은 기존 고정 대기 설정을 유지한다.

- 정상 리뷰 0건은 성공이며 실패·차단 집계에 포함하지 않는다.
- 명확한 접근 차단 예외는 상품 요청 직후 수집을 끝내고 추가 리뷰 요청을 하지 않는다.
- `/status`는 상품별 최신 실패를 원인별로 집계하고 대기 상품 수·가장 이른 재시도 가능 시각을 보여준다. 이는 실행 확정 시각이 아니며 TTL, 큐 여유, Backfill 수집 중지 설정도 적용된다.
- 원본 오류·리뷰 본문·작성자·토큰은 운영 집계에 포함하지 않는다.
- 마이그레이션 `c79fa18d2e60`은 기존 데이터를 삭제하지 않고 nullable 열 두 개와 상품별 이력 조회 인덱스를 추가한다.

## 옥션·G마켓 정상 경로 재검증 (#112)

2026-10-11 운영 Data API 컨테이너에서 각 collector의 정상 검색(`텀블러`, 최대 1상품)을 실행했다. 양쪽 모두 검색 단계에서 접근 차단으로 끝났다. 상품·리뷰를 DB에 저장하거나 AI 분석 요청을 보내지 않았다. 검색이 막힌 이후 상세·리뷰 요청을 계속하지 않았다.

| 플랫폼 | 검색 | 상세·리뷰 실수집 |
| --- | --- | --- |
| 옥션 | 접근 차단 | 검색 차단으로 미검증 |
| G마켓 | 접근 차단 | 검색 차단으로 미검증 |

이번 변경으로 수집 성공을 주장하지 않는다. 정상 접근이 가능해지면 기존 검색·상세·리뷰 경로를 순서대로 다시 검증해야 한다.

오류 대응은 다음과 같이 보완했다.

- HTTP 403/429와 명확한 차단 화면은 `AccessBlockedError`로 즉시 끝낸다. 수집 워커는 상품 단계 차단 후 리뷰 요청을 하지 않는다.
- 404/410과 5xx 응답은 셀렉터를 기다리지 않고 HTTP 오류로 보고하여 상품 없음과 일시 장애를 구분한다.
- 옥션 리뷰 응답이 JSON이 아니거나 `d`가 문자열이 아닌 경우는 응답 형식 오류다. 모든 HTTP/JSON 오류를 차단으로 묶지 않는다.
- G마켓 리뷰 요청의 일반 브라우저 오류만으로 Cloudflare 차단을 단정하지 않는다.
- 확인된 실패는 #111의 원인별 정기 재예약 대기와 상태 집계에 반영된다.
- 차단 감지, HTTP/응답 형식 구분, 단일 요청 후 중단, 정상 검색/상세/리뷰 파서의 단위 테스트를 유지한다.

## 상태 집계 응답 지연 (#118)

운영 `/status/api/overview`가 30초 제한을 넘었고, 요청 중 플랫폼별 리뷰 수의 상관 서브쿼리가 PostgreSQL `DataFileRead`로 실행되는 것을 확인했다. 기존 쿼리는 각 플랫폼마다 리뷰를 다시 읽고 전체/최근 관측 지표도 별도 스캔했다.

리뷰의 플랫폼별 수·전체 수·최근 신규/재관측 수를 하나의 그룹 집계에서 계산하도록 변경했다. 상품은 별도로 작은 그룹 집계를 수행해 리뷰 없는 플랫폼도 0건으로 유지한다. 목표 버전별 분석 집계·시간대 그래프·10초 캐시·화면의 중복 갱신 방지(busy)는 유지한다.

- 운영 DB의 EXPLAIN 예상 비용: 기존 플랫폼 집계 약 269,728 → 새 리뷰 그룹 집계 약 48,636. 이는 실행 시간 비율이 아닌 플래너 예상 비용이다.
- 새 overview 함수 전체를 운영 DB에 읽기 전용으로 실행한 결과 9.24초, 5,445상품·583,887리뷰 집계를 확인했다. 요청 부하·캐시·IO에 따라 응답 시간은 달라진다.
- PostgreSQL 통합 테스트에서 신규 리뷰/재관측 리뷰/이전 리뷰 및 리뷰 없는 플랫폼의 집계 값을 검증했다.

## 차단 응답 분류와 플랫폼 단위 대기 (2026-10-14, #141)

10/14 15시(KST)부터 운영 서버의 올리브영 리뷰 API(`m.oliveyoung.co.kr/review/api/v2/reviews/cursor`)가 모두 403(Cloudflare '잠시만 기다려 주세요' 화면)으로 실패했다. 같은 요청이 다른 IP에서는 200이라 운영 서버 IP에 대한 요청 제한으로 본다. 무신사도 10/14 01시(KST)에 429가 7건 있었다. 두 응답 모두 `unknown`으로 분류돼 상품별로 1시간만 쉬었고, 같은 플랫폼의 다른 상품은 계속 요청했다.

- `httpx.HTTPStatusError` 403·429는 `blocked`, 404·410은 `not_found`, 5xx는 `network`로 분류한다. 이전 이력의 '403 Forbidden'·'429 Too Many Requests' 문구도 차단으로 읽는다.
- 플랫폼의 마지막 차단 완료가 마지막 성공보다 새로우면 차단 상태다. 차단 후 `SCHEDULE_PLATFORM_BLOCK_SECONDS`(기본 3600초) 동안은 대기, 그 뒤에는 시험 단계다.
  - 대기: 스케줄러가 예약하지 않고, 워커도 이미 예약된 자동 작업(스케줄러·발굴·시드)을 꺼내지 않는다. 이 작업은 큐 여유 계산에서 뺀다. 사람이 요청한 작업은 그대로 실행한다.
  - 시험: 스케줄러는 진행 중 작업이 없을 때 한 건만 예약하고, 워커도 그 플랫폼 작업을 한 번에 하나만 실행한다. 성공하면 평소대로 돌아오고, 다시 차단되면 대기로 돌아간다.
  - 자동 발굴은 차단 상태 플랫폼에 검색을 보내지 않는다.
- 차단을 우회하지 않는다. 요청을 멈추고 간격을 두어 회복을 기다린다.

## 플랫폼별 수집 간격 (2026-10-15, #147)

올리브영은 10/15 01~04시(UTC)에 차단이 풀린 뒤 밀린 상품을 시간당 230건 넘게 수집했고 약 3시간 뒤 다시 403으로 차단됐다. 10/9~13일에는 시간당 50~70건으로 며칠간 정상이었다. 무신사도 429가 간헐적으로 난다.

- `COLLECTION_PLATFORM_INTERVALS`(기본 `oliveyoung=80,musinsa=60`)로 플랫폼별 자동 수집 작업의 최소 시작 간격(초)을 둔다. 올리브영은 시간당 최대 45건, 무신사는 60건이다.
- 워커는 같은 플랫폼의 직전 작업 시작(`locked_at`) 뒤 간격이 지나야 다음 자동 작업(스케줄러·발굴·시드)을 꺼낸다. 사람이 요청한 수집은 제외한다.
- 스케줄러는 주기(기본 300초)마다 간격 플랫폼에 `ceil(주기/간격)`에서 대기 중 자동 작업 수를 뺀 만큼만 예약하고, 나머지 자리는 다른 플랫폼으로 채운다.
- 간격은 차단 대기·시험 단계(#141)와 함께 적용된다. 차단 대기 중인 플랫폼에는 예약하지 않는다.
- 워커가 여럿이어도 간격이 지켜지도록 간격·시험 단계가 켜져 있으면 claim을 advisory lock으로 직렬화한다.
- 간격 설정은 시작할 때 형식(`플랫폼=초`, 0 이상 정수)과 상한(3600초)을 검증한다. 최근 시작 시각을 1시간까지만 보기 때문이다.
- 큐 여유가 작을 때 같은 플랫폼만 먼저 받지 않도록 가장 오래 쉰 플랫폼부터 몫을 배분한다. 발굴 등으로 몫보다 많이 쌓인 작업은 큐 여유 계산에서 뺀다.
