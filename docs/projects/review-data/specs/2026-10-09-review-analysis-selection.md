> 중복 통합 적용 후 source_review_count는 DB 원본 행 전체가 아닌 대표 리뷰 집합의 크기다. 대표 선택·원본 보존·리뷰0건 상품 제외는 [중복 정책](2026-10-09-review-deduplication.md)을 따른다. 아래500건 표본 정책은 그 대표 집합에 적용한다.

# 리뷰 분석 전송·대표 표본 기준

## 어떤 리뷰를 분석하는가

수집 워커가 정상적으로 저장한 상품별 리뷰를 분석한다. 기준 모집단은 Data DB 원본 리뷰를 중복 통합한 **상품별 대표 리뷰 집합**이며, 쇼핑몰 화면에 표시된 전체 리뷰 수가 아니다. 수집기가 첫 페이지나
일부 리뷰만 제공하면 분석도 그 저장 범위에 한정된다.

| 중복 통합 후 대표 리뷰 수 | 전송 기준 |
|---|---|
| 0건 | 분석 요청을 만들지 않는다. |
| 1~500건 | 대표 리뷰 전체를 하나의 요청에 전송한다. |
| 501건 이상 | 별점 분포를 반영한 최대500건의 대표 표본을 하나의 요청에 전송한다. |

운영 설정은 AI_MAX_REVIEWS=500, 선택 정책 버전은 rating-stratified-v1이다.
별도로 상한을 낮추면 그 상한부터 표본을 사용한다. AI의 한 요청500건 제한을 지키며
전체 리뷰를 여러 요청으로 분할해서 분석·병합하는 방식은 사용하지 않는다.

## 분포를 나누는 기준

**분석 전 원본 별점**을 사용한다. 아직 계산되지 않은 RTI나 텍스트 감성 점수로 고르지 않는다.
별점 구간별로 나눈 뒤 각 구간의 저장 건수에 비례해 표본 수를 할당한다.

| 구간 | 원본 별점 |
|---|---|
| 0 | 0점 |
| 1 | 0점 초과~1점 이하 |
| 2 | 1점 초과~2점 이하 |
| 3 | 2점 초과~3점 이하 |
| 4 | 3점 초과~4점 이하 |
| 5 | 4점 초과~5점 이하 |
| unrated | 별점 미제공(null) |

5점 척도의 정수 별점은 각 별점별 구간에 들어간다. 소수 별점은 위 범위로 분류한다.
별점이 없으면0점으로 바꾸지 않는다. 범위 밖 값·비유한 값은 별도 outside_scale/
invalid_rating 구간으로 분리하며 임의로 정상 별점으로 보정하지 않는다.
이 구간 분류는 원본 별점에 대한 것이며, AI 결과 점수의 -1→NULL 변환과 별개다.

## 각 구간에서 몇 건을 고르는가

기본 목표 건수는 `표본 상한 × 구간 대표 리뷰 건수 / 전체 대표 리뷰 수`다.

1. 실제 최저·최고 별점 리뷰를 우선 확보한다. 별점이 서로 다르면 각각1건을 포함한다.
2. 존재하는 각 구간을 최소1건 보존한다. 같은 구간에 두 극값이 있으면 최소2건이 필요하다.
3. 구간별 목표 건수의 정수 부분을 배정하되 위 최소 건수를 지킨다.
4. 합계가 상한보다 적으면 목표보다 덜 배정된 구간에 잔여 건수를 분배한다.
5. 최소 보존 때문에 합계가 상한을 넘으면 최소 건수 이상의 구간에서 초과 배정을 줄인다.

결과는 정확히 상한만큼의 서로 다른 리뷰다. 소수 구간과 극값을 보존하므로 희소 구간에서
순수 비례값과 약간 차이가 날 수 있다. 운영 상한500은 모든 구간과 두 극값을 보존하기에
충분하다. 상한1 같은 작은 별도 설정에서는 최저 별점만 보존할 수 있다.

예시: 저장 리뷰2,000건을500건으로 선택한다.

| 구간 | 원본 | 표본 |
|---|---:|---:|
| 1점 | 100 | 25 |
| 2점 | 200 | 50 |
| 3점 | 300 | 75 |
| 4점 | 500 | 125 |
| 5점 | 800 | 200 |
| 별점 없음 | 100 | 25 |
| 합계 | 2,000 | 500 |

예를 들어9,998건이5점이고1건이1점,1건이별점 없음이라면
희소한1점과 별점 없는 리뷰를 각각 보존하고 나머지를5점 구간에서 선택한다.

## 같은 구간 안에서 어떤 리뷰를 고르는가

극값으로 확보한 리뷰를 제외하고 `작성 시각 → 원본 리뷰 ID` 순서로 정렬한다.
남은 할당이1건이면 중간 리뷰를 선택하고,2건 이상이면 정렬된 집합의 양 끝을 포함해
등간격으로 선택한다. 최신 리뷰에만 몰리지 않도록 저장된 작성 시점을 분산한다.
작성 시각이 없으면 빈 시각으로 정렬하며 실제 작성일을 추정하지 않는다.

같은 입력·상한·선택 정책은 같은 표본을 만든다. 최종 요청은 원본 리뷰 ID 순서로 정렬한다.
임의 추첨, 리뷰 본문 수정, 점수 조작, 동일 리뷰 중복 선택은 하지 않는다.

## 언제 다시 보내는가

리뷰 저장 후 분석 작업을 생성하고 분석 워커가 AI에 POST한다. 응답 SSE의 최종 결과를
검증한 뒤 DB 결과 저장과 완료 처리를 같은 트랜잭션으로 수행한다.

- 저장 리뷰 ID·본문·별점·작성일 또는 모델/정책/표본 조건이 바뀌면 새 작업을 만든다.
- 같은 입력과 조건이면 기존 작업·완료 결과를 재사용한다. 재수집만으로 매번 다시 분석하지 않는다.
- 전체 저장 리뷰 해시로 비교하므로 표본에 선택되지 않은 리뷰의 변경도 감지한다.
- 재시도는 저장된 입력 스냅샷과 같은 Data 작업 ID를 사용한다. 표본을 새로 추첨하지 않는다.
- X-Request-ID와 Idempotency-Key 모두 그 작업 ID를 사용해 중복 계산을 막는다.

## 결과를 해석하고 표시하는 기준

| 필드 | 의미 |
|---|---|
| sampled | 대표 표본 분석 여부 |
| source_review_count | 분석 입력 선택 시 중복 통합된 대표 리뷰 수 |
| review_count / input_review_count | 실제 분석에 전송한 리뷰 수 |
| sampling.source_rating_distribution | 구간별 원본 건수 |
| sampling.sample_rating_distribution | 구간별 표본 건수 |
| sampling.policy_version | 선택 정책 버전 |
| sampling.max_reviews | 당시 표본 상한 |

리뷰별 결과는 실제 분석한 리뷰에만 붙인다. 비선택 리뷰에는 점수를 만들지 않는다.
목록의 평균 RTI는 최신 완료 작업의 제공된 RTI만 평균하며 NULL은 제외하고0은 포함한다.
계산 가능한 RTI가 없으면 평균도NULL이다. 표본 평균을 전체 리뷰의 확정 점수로 표현하지 않는다.
표본의 network 점수 역시 선택 집합의 결과이며 전체 쇼핑몰 리뷰 네트워크에 대한 점수가 아니다.

관련 구현: core/analysis_sampling.py, core/db/analysis_repository.py,
core/service/catalog.py. 관련 운영 흐름: [[2026-10-09-analysis-catalog]].


## 중복 통합과 전송 전 처리

같은 상품에서 본문·별점·작성자·작성일·구매 옵션·이미지가 모두 같은 리뷰만 통합한다. 작성자가 없거나 공백이거나 작성일이 없으면 별개의 리뷰로 유지한다. 본문만 같은 다른 작성자의 리뷰는 통합하지 않는다.

- 대표는 최초 저장 시각, 동률이면 리뷰 ID 순서로 정한다. 원본 행·원본 ID·과거 분석 결과는 삭제하지 않는다.
- 같은 저장 배치에 같은 리뷰 ID가 반복되면 마지막 관측값을 한 번만 저장한다. 이는 서로 다른 ID의 내용 중복 통합과 별개다.
- PostgreSQL에 저장할 수 없는 NUL 문자를 본문·작성자·옵션·이미지 URL에서 제거한다. 제거 후 빈 본문은 저장하지 않는다.
- 상품에 저장 리뷰가 없으면 분석 요청을 생성하지 않으며 일반 검색·카탈로그에서 제외한다. 운영 대시보드에서는 원인 점검을 위해 표시한다.

따라서 `/status`의 **원본 리뷰 행 수**와 분석 메타데이터의 **source_review_count**는 다를 수 있다. 대표 집합을 확정한 다음 위 500건 표본 정책을 적용한다.

## 실제 운영에서 확인한 선정 예시

무신사 상품858911은 대표 리뷰800건에서500건을 전송했다. 작업2301에서 선택 ID와 저장된 결과500개가 일치했고 API 전체 페이지의 중복은0개였다.

| 별점 | 대표 집합 | 전송 표본 |
|---|---:|---:|
| 0 | 6 | 4 |
| 1 | 4 | 2 |
| 2 | 1 | 1 |
| 3 | 11 | 7 |
| 4 | 91 | 57 |
| 5 | 687 | 429 |
| 합계 | 800 | 500 |

최저0점·최고5점과 희소2점 구간을 보존하면서 전체 분포를 반영했다. 이 수치는 해당 검증 시점의 스냅샷이며 현재 상품의 리뷰 수를 의미하지 않는다.

## 모델 업데이트 시 선정과 결과 유지

목표 `model_version`·`policy_version`이 바뀌면 저장된 대표 집합에서 같은 선정 규칙으로 새 작업을 생성한다. 모델만 바뀌고 입력·상한·선정 정책이 같으면 선택 리뷰도 같다. 모든 리뷰를 새로 수집한 뒤 분석하는 것은 아니다.

- 목표 버전과 현재 입력·선정 조건에 맞는 완료 상품은 재분석 대상에서 제외한다.
- 일시적 재시도는 같은 작업 ID·같은 요청 스냅샷을 사용한다. 버전 변경과 종료된 실패의 명시적 재실행은 새 ID를 사용한다.
- 새 결과의 리뷰 ID·건수·모델/정책·점수 규격을 검증하고 DB에 모두 저장한 후 표시 결과를 전환한다.
- 새 분석 대기·실행·실패 중에도 이전 성공 결과를 유지한다. 조회의 `is_current=false`, 목표 버전과 `refresh_job`으로 이전 결과임을 구분한다. 이전 결과를 새 모델 결과라고 표시하지 않는다.
- 재분석 진행 방식은 [모델 버전별 재분석](2026-10-10-analysis-refresh.md)을 따른다.

대표 표본의 점수는 선택된 리뷰에 대한 결과다. 미선택 리뷰의 점수는 만들지 않으며 AI의 network 신호도 전송 집합을 기준으로 해석한다. 전 리뷰 분석·배치 간 network 집계가 필요하면 별도 계약이 필요하다.
