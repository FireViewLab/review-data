# Data 운영 대시보드

## 접속과 인증

- 운영 화면: `https://data.re-view.kr/status` (같은 서버의 `data.beens.kr/status`도 사용 가능).
- 화면 틀만 공개한다. 데이터 API는 기존 Data `INTERNAL_TOKEN` 또는 대시보드 로그인 쿠키가 필요하다. AI 인증 토큰과는 다르다.
- 로그인은 `POST /status/login`, 로그아웃은 `POST /status/logout`이다. 토큰은 브라우저 저장소에 저장하지 않는다. `/status`에만 적용되는 HttpOnly·SameSite=Strict 쿠키를 8시간 발급한다. HTTPS에서는 Secure를 설정한다.
- `SPRING_AUTH_LOGIN_URL`을 설정하면 로그인 창이 이메일·비밀번호를 받는다. Data 서버가 Spring 로그인 API를 대신 호출하고 응답 role이 `ADMIN`일 때만 같은 쿠키를 발급한다. 비밀번호와 Spring 토큰은 저장·기록하지 않는다. 자격 증명 오류와 권한 부족은 같은 401로 응답하며, 실패는 계정당 15분에 5회·전체 30회로 제한한다(429). Spring 장애 시에는 503이며 내부 토큰 로그인으로 전환할 수 있다. Spring 코드는 변경하지 않는다.
- 쿠키는 기존 수집 API를 인증하지 않는다. 운영 응답은 `Cache-Control: no-store`이다. 로컬에서 내부 토큰 미설정 시 기존 개발 인증 정책과 같이 열려 있다.

## 표시 항목

- 등록 상품, 원본 리뷰 행 수, 과거 이력을 포함한 분석 결과 행 수, 진행 중 수집·분석 작업 수.
- 서버 CPU 사용률(누적 tick 차이), 메모리 사용률(MemAvailable 기준), 1/5/15분 부하. Linux `/proc`의 시스템 총계를 읽는다. Docker cgroup 자원 한도가 아닌 호스트 값이며 추가 호스트 디렉터리나 Docker socket을 마운트하지 않는다.
- 디스크는 API 파일시스템의 용량과 사용량이다. 별도 DB 볼륨·컨테이너별 사용량을 따로 측정한 값은 아니다. 최초 CPU 표본과 Linux proc 정보가 없는 로컬 환경에서는 계산 가능한 자원만 표시한다.
- 최근 15분 신규 저장·저장/갱신·수집 완료·AI claim·AI 완료 처리량. AI claim은 작업 획득 기준 근사치이며 정확한 네트워크 POST 횟수·바이트 계측이 아니다. 재시도에서는 마지막 claim 시각만 남는다.
- 최근 1시간 신규 리뷰 저장 및 분석 완료 리뷰의 5분 구간 그래프. 현재 구간은 진행 중이다.
- 워커와 스케줄러 heartbeat: 10초마다 별도 DB 세션으로 갱신한다. 35초 이상 응답이 없거나 정상 종료하면 오프라인으로 표시한다. 실행 중 작업은 locked_by로 연결한다. idle 워커도 생존 여부를 확인할 수 있다. 실행 중은 작업 성공을 보장하는 의미가 아니다.
- 수집·분석 대기/실행/lease 만료/재시도 소진, 가장 오래된 대기, 독립 발굴 순환 위치·다음 실행·최근 등록/예약/실패.
- 플랫폼별 저장 상품·원본 리뷰, 최신 분석 상태, 리뷰0건 원인, 최신 수집 실패.

## 상세 조회

- 수집/분석 작업은 상품명·상품 ID·플랫폼·상태로 검색한다. 최신 ID부터 cursor로 페이지 이동한다.
- 수집 상세와 상품 리뷰 상세는 **현재 저장된 원본 리뷰**를 보여준다. 특정 수집 작업에서 저장한 건수나 중복 통합된 대표 집합 수와 다를 수 있다. 작업 없는 상품도 직접 리뷰를 조회할 수 있다.
- 분석 상세는 당시 `input_payload`의 리뷰 스냅샷과 `analysis_job_id + review_id`로 대응하는 저장 결과를 나란히 제공한다. 나중에 리뷰 본문이 바뀌어도 전송 당시 내용은 유지한다.
- 전송 표본 수·원본 대표 집합 수·표본 방법·작업 ID·모델/정책·점수·등급·근거를 확인한다. RTI와 각 신호의 null은 계산 불가이며 0으로 바꾸지 않는다.
- AI 결과는 검증 및 DB 트랜잭션 저장 이후 나타난다. 처리 중 SSE 이벤트나 임시 점수를 실시간으로 게시하는 화면은 아니다.
- 상세는 기본50건, 최대100건씩 조회한다. 리뷰 본문은 HTML로 실행하지 않고 문자열로 표시한다. 작성자·raw_payload·원본 오류·인증 헤더 값은 제공하지 않는다.

## 조회 엔드포인트

- `GET /status/api/overview`: 10초 캐시된 운영 집계. 화면도10초 자동 갱신한다.
- `GET /status/api/jobs/{collection|analysis}`: 작업 목록.
- `GET /status/api/jobs/{collection|analysis}/{id}`: 작업과 요청/저장 데이터 상세.
- `GET /status/api/products`: 상품 목록(운영 점검을 위해 리뷰0건도 포함).
- `GET /status/api/products/{platform}/{product_id}/reviews`: 해당 상품 원본 리뷰.

운영 화면은 조회 전용이다. 재수집·재분석·데이터 삭제 버튼은 제공하지 않는다. Spring·프론트와 공용 Product/Review 계약을 변경하지 않는다.


## 종료된 워커 목록 정리

정상 종료로 stopped_at이 기록된 워커·스케줄러는 다음 화면 갱신에서 숨긴다. 정상 종료 기록 없이 신호가 끊긴 경우35초부터 오프라인으로 표시하고 마지막 신호5분이 지나면 목록에서 숨긴다. 각 역할에 정상 heartbeat가 없다는 경고는 유지하므로 목록에서 빠져도 역할의 장애 상태를 확인할 수 있다. 화면과 집계 캐시는10초마다 갱신한다. DB heartbeat 이력은 화면 표시와 별도로 기존7일 보관·자동 삭제 정책을 유지한다.


## 저장 분석 결과 집계

저장 분석 결과 카드는 현재 DB 목표 모델·정책 버전과 일치하는 상품별 최신 성공 작업의 리뷰 결과 행 수를 표시한다. 같은 상품·같은 버전의 재분석 이력도 여러 번 합산하지 않는다. 정상 done과 결과가 보존된 완료 stale 작업을 성공 이력으로 인정한다. 목표 미설정 시0건과 미설정 안내를 표시한다. 이전 버전 이력과 실패·진행 중 요청은 이 카드에서 제외하며 DB 및 작업 상세 이력은 유지한다. 저장 리뷰 카드는 원본 리뷰 전체 행 수여서500건 대표 표본 분석 결과 수와 다를 수 있다.

## Backfill 종료 화면 (2026-10-12)

- 종료된 캠페인은 재분석 영역의 캠페인 목록에서 항목 자체를 완료 상태로 표시한다(초록 테두리·진행 막대, 실패가 있으면 주황). 항목 안에 종료 시각, 소요 시간, 완료/대상, 목표 버전 적용률(완료 ÷ 제외를 뺀 대상), 실패·제외 건수를 둔다. 접고 펴는 영역이나 별도 요약 영역은 두지 않는다.
- 최신 캠페인의 실패 건은 최근 50건까지 상품·작업 ID·실패 원인·시도 횟수·실패 시각을 항목 안에 보여주고 재시도 버튼을 함께 둔다. 원인은 구분 값만 제공하며 저장된 오류 문구는 내보내지 않는다. 구분 기록 이전의 실패는 '원인 미기록'으로 표시한다.
- 발굴이 Backfill 진행, 분석 대기열 기준 초과(`DISCOVERY_MAX_ANALYSIS_PENDING`), 수집 대기열 기준 초과로 건너뛰는 경우 발굴 영역에 사유를 표시한다.

## 운영 개요 응답 (2026-10-12)

- 개요 집계는 운영 DB에서 약 15초가 걸렸다. 캠페인 집계가 완료 작업 전체의 `input_payload`(상품당 리뷰 수백 건)를 읽는 것이 6초를 차지해, 진행 중 항목과 최근 15분 완료분에서만 읽게 했다(6.3초 → 0.05초). 리뷰 전체를 훑는 합계 때문에 전체 집계는 여전히 약 8초다.
- 화면은 두 API로 나눠 갱신한다.
  - `GET /status/api/live`: 대기열, 워커와 처리 중 작업, 캠페인 진행과 실패 건, 발굴 상태, 서버 자원, 분당 처리량 중 작업 기준 값. 5초마다 읽는다. 서버는 2초 캐시로 여러 브라우저의 조회를 묶는다.
  - `GET /status/api/overview`: 위 값에 더해 상품·리뷰·분석 결과 합계, 플랫폼별 수치, 추이 그래프, 리뷰 없는 상품과 수집 실패 집계. 직전 집계를 즉시 응답하고 `refreshing`으로 갱신 중임을 알린다. 갱신은 백그라운드에서 한 번에 하나만 돌고, 주기는 60초와 직전 집계 시간의 2배 중 큰 값이다. `refresh=true`는 주기를 기다리지 않고 갱신을 시작한다.
- 화면 머리글은 '실시간'과 합계 기준 시각을 따로 표시한다. 새로고침 버튼은 실시간 값을 바로 다시 읽고 합계 갱신을 요청하며, 끝날 때까지 '갱신 중'을 표시하고 2초마다 확인한다.
- 서버 재시작 직후와 제어 요청(시작·중지·재시도) 직후에는 합계 영역만 집계가 끝날 때까지 '집계 중'으로 남고, 실시간 영역은 바로 표시된다.

## 합계 집계 단축 (2026-10-13)

운영 측정(캐시가 비어 있을 때): 추이 그래프의 신규 리뷰 조회 3.5초(리뷰 전체 스캔), 저장 분석 결과 수 7.8초(분석 결과 67만 행 조회), 플랫폼별 리뷰 수 3.1초, 리뷰 없는 상품 수 4.0초.

- `reviews(first_collected_at)` 인덱스(`idx_reviews_first_collected_at`, 마이그레이션 `a3d51c7e4f20`)를 CONCURRENTLY로 추가해 추이 조회를 범위 조회로 바꾼다. 최초 수집 시각은 바뀌지 않아 재관측 UPDATE 비용은 늘지 않는다. `last_collected_at`에는 인덱스를 두지 않는다(재관측마다 값이 바뀌어 쓰기 비용이 커진다).
- 저장 분석 결과 수는 결과 행을 세지 않고 상품별 최신 목표 버전 작업의 `result.review_count` 합으로 계산한다. 운영 데이터에서 작업 5,073건 모두 결과 행 수와 일치했다(합계 676,058, 0.16초).
- 플랫폼별 리뷰 수와 리뷰 없는 상품 수는 전체를 세야 하는 값이라 그대로다. DB 컨테이너 메모리 512MB·`shared_buffers` 128MB에 DB가 1.4GB라 스캔이 디스크를 읽는 것이 남은 지연의 원인이다.
